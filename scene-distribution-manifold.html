Scene Distribution Manifold

Probabilistic Modeling Robotics Simulation Uncertainty Quantification

Overview

Training or evaluating a robot in simulation against one fixed scene tells you almost nothing about how it behaves in the real world, where floors are sometimes wet, lighting shifts, and objects show up in combinations nobody scripted. This project models the space of scenes a robot might encounter as an explicit probability distribution, parameter by parameter, with the physical couplings between parameters made explicit, rather than as a handful of hand-picked test scenes.

A "scene distribution" here is a concrete, versioned object: a set of parameter marginals (e.g. floor state, ambient lighting, surface friction), the conditional rules that couple them when they aren't physically independent (a puddle doesn't just change the floor's appearance, it also drops its friction coefficient), and a handful of named worst-case scenarios called out explicitly. Every value in it carries a provenance tag, cited from a source, estimated, or unknown, so it's clear what's grounded and what isn't.

Approach

The pipeline has four stages:

1 Input

A curated library of phenomenon YAML files, each modeling one real-world hazard.

↓
2 Composition

A headline manifest combines several phenomena into one frozen scene distribution.

↓
3 Sampling

A quasi-Monte Carlo sampler draws scenes and applies any triggered coupling rules.

↓
4 Checking

Every scene is re-validated against those rules and flagged for provenance.

  1. Input: a curated phenomenon library. 39 YAML files across four domains (home, kitchen, warehouse, contact-rich manipulation), each modeling one real-world hazard or failure mode as a self-contained set of parameter distributions, coupling rules, and named worst-case scenarios.
  2. Composition. A buyer- or scenario-specific "headline" manifest names which phenomena to combine (every shipped headline composes exactly 4) and the composer concatenates their marginals, conditional rules, and named scenarios into one frozen scene distribution, layering in any scenario-specific parameters on top.
  3. Sampling. A quasi-Monte Carlo sampler draws concrete scene instances (Latin-hypercube or Sobol sequences through the inverse CDF of each marginal, for even coverage of the parameter space) and applies each conditional rule's override whenever its trigger condition holds in that sample, rather than sampling coupled parameters independently. A separate sampler emits the hand-authored named scenarios directly, as fixed worst-case draws.
  4. Checking. Every sampled scene, random or named, is run back through the same coupling rules to catch any combination that shouldn't co-occur, and through a provenance summary that flags which of its parameters are still only estimated rather than grounded in a cited source.
Worked example
Sampled bathroom_floor_state = puddle
→ triggers rule puddle_drops_friction
Overridden bathroom_friction_coefficient uniform(0.15, 0.65) → uniform(0.15, 0.40)
↓ guarantees
Result Friction stays below the ANSI A1264.2 slip-resistant threshold (0.42) whenever a puddle is present.

The two parameters move together instead of being drawn independently, so a sampled scene never shows a puddle on a floor the model still treats as high-friction.

Results

  • Coupling rules are enforced, not just declared. Sampling and checking share the same rule engine, so a conditional like "a puddle drops the floor's friction coefficient" is applied during generation and re-verified afterward, rather than being documentation that the sampler is free to ignore.
  • Named worst-case scenarios ship alongside the random population. Every phenomenon can define fixed, hand-authored edge cases, like a puddle under low light, that are always included rather than left to chance.
  • Every parameter carries a provenance tag, so it's always clear whether a given value is grounded in a cited source or still an estimate awaiting verification.
